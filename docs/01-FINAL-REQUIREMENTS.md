# Presentify — Final Requirements Specification (v1)

> **Status:** for owner confirmation. Implementation starts after confirmation.
> Background analysis, questions and lessons from the earlier version: [00-DISCOVERY.md](00-DISCOVERY.md) (this document supersedes it where they differ).

**Product:** Presentify — *Present. Scan. Access.* — "One Presentation. One QR Code. Zero Unnecessary Paper."
**Repository:** `rajmanasu-a11y/Presentify` — standalone.
**Platform:** **self-hosted Supabase** (free, open-source) — first on the owner's laptop, later on a State Data Centre server. No Supabase Cloud plan is needed, so the Supabase Cloud free-plan limits (1 GB storage, project pausing) do not apply; the only limits are the server's own disk and memory.

## 4. Main workflows

**Admin:** Create Meeting wizard (details → presenters → sessions & presentations → supporting material → access & downloads → QR → review & publish) → *Meeting Published Successfully* with QR, link, Display / Download / Print / Copy.
**Participant:** Scan QR → Name / Designation / Organisation (+ configured fields, consent) → presentation and supporting material → download if permitted. English/ಕನ್ನಡ switch at the top.
**After the meeting:** Participants → Attendance → Access/Download activity → Export PDF/Excel/CSV → Archive.

**Statuses:** Draft → Published (shown automatically as Scheduled / Active / Completed from the meeting times; admin can end early or extend) → Archived.
**Versions:** replacing a file creates a new version (uploaded by, time, file name, change notes); an admin can restore an older version.

### 4.1 Mobile document viewer (owner requirement)
PDFs must **fit the full screen of any smartphone**:
- Opens at **fit-to-width** in portrait and **fit-to-screen** in landscape; re-fits automatically on rotation and on any screen size (small Android phones to tablets).
- **Full-screen button** hides all Presentify controls so the page uses the entire screen; swipe left/right or tap edges to change page; page number shown briefly.
- Pinch-to-zoom and double-tap zoom; sharp rendering on high-resolution screens; pages load progressively so a 100-page PDF opens quickly.
- Slides (landscape) show a gentle "Rotate your phone for a larger view" hint in portrait.
- Honest limitation: on **iPhone Safari**, web pages cannot enter true browser full-screen; Presentify's full-screen mode fills the whole visible page and Safari's own address bar shrinks when scrolling. Android Chrome supports true full screen.
- Tested on emulated 320 px, 360 px, 390 px, 412 px, 768 px widths and on real Android/iPhone devices during your acceptance.

## 5. Technology (decided)

| Part | Choice | Plain-language reason |
|---|---|---|
| Platform | **Self-hosted Supabase** (PostgreSQL, Auth, Storage, Edge Functions, API gateway) | Free and open-source; runs on your laptop and on a government server alike; keeps all data on your own machines. |
| Database | PostgreSQL (inside Supabase) with **Row-Level Security** | The database itself refuses to show one organisation's data to another — not just the screens. |
| Staff login | Supabase Auth (e-mail + password, authenticator-app MFA); public sign-up **disabled** — accounts are created only by administrators | Proven login system with MFA built in. |
| Server logic | Supabase **Edge Functions** (TypeScript) | Public QR pages, participant registration, file access checks, uploads, limits — all checked on the server. |
| Screens | **React + TypeScript**, built into static files and served by nginx in front of Supabase | Fast, accessible screens; one web address for everything. |
| Participant pages | Small, separately loaded part of the app (target < 150 KB) | Opens quickly on any phone when hundreds scan at once. |
| PDF viewer | PDF.js (built in, no third party) | §4.1. |
| QR codes | Generated inside Presentify (SVG/PNG) from a random token | No external QR service. |
| Live participant count | Refreshes every few seconds for authorised staff | Simple and light on the server. |
| Reports | Browser print layouts (PDF), Excel and CSV produced in the browser | Correct Kannada; no extra server software. |
| Languages | English + Kannada text catalogues; Noto Sans Kannada font bundled | Works without internet; Hindi addable later. |
| Packaging | **Docker Compose** | Same package on the laptop and the State Data Centre. |

**Supabase Studio** (Supabase's own database admin screen) is never exposed to the network; it is reachable only from the server itself (or not installed at the State Data Centre).

## 6. Security and privacy

### 6.1 Organisation isolation
Every organisation-owned table carries `organisation_id`; Row-Level Security policies compare it with the organisation stored in the signed-in user's login token (added by a Supabase Auth hook from the user's profile, not editable by the user). Child records use composite keys so they cannot point at another organisation's data. Automated tests try to read and change another organisation's data through every route.

### 6.2 Participants and QR
- Participants do not get database access. Every participant action goes through Edge Functions which check the QR token, the meeting's availability window, passcode and limits.
- QR token: ≥ 128-bit random, URL-safe, contains no IDs or personal data, revocable, expirable. Invalid/expired/revoked tokens give plain-language messages.
- After registration the participant's browser holds a meeting-only access token (random, stored hashed); files are opened through **short-lived signed links** (about 60 seconds) issued only after checks; downloads get a download link only when permitted.
- Rate limits on public endpoints (per IP and per meeting).

### 6.3 Uploads
Allowed file types per organisation; extension **and** file content signature checked; size limit per organisation; storage quota checked before the upload starts and verified after it finishes; random storage names; private storage buckets only (the earlier version's public bucket is not repeated). HTML/SVG/script files are never displayed inline. ZIP files are stored, never unpacked on the server.

### 6.4 Other controls
Password policy and lockout; MFA; administrators reset passwords until an e-mail server is configured; append-only audit log (database triggers) for every action in requirement §29; strict Content-Security-Policy; secrets (JWT secret, service key) only in server configuration, never in the browser; HTTPS-only at the State Data Centre; IP/device data retained 90 days.

## 7. Environments

### Stage 1 — Owner's laptop
- Install **Docker Desktop**; one command starts Presentify and its Supabase services.
- Recommended **16 GB RAM** (minimum 8 GB), 30 GB free disk — self-hosted Supabase runs about ten small services.
- **Phones:** laptop and phones on the same Wi-Fi (a mobile hotspot works best; office Wi-Fi often blocks phone-to-laptop traffic). QR points to the laptop's network address.
- **Test mode uses plain HTTP**, because phones do not trust home-made certificates. Screens show *"Test mode — not for official use"*; do not collect real personal data in this mode.

### Stage 2 — State Data Centre
- Linux server (RHEL/Ubuntu), Docker; HTTPS with the official domain certificate; Studio not exposed; firewall rules documented.
- Prepared for the **CERT-In empanelled security audit** usually required before go-live (OWASP Top 10 / ASVS Level 2 controls and documentation).

---

## 8. Backups (NAS)
- Nightly: PostgreSQL backup (database, including logins and audit) + copy of the stored files + configuration (without secrets in plain text) to a folder on the **network storage drive**.
- Retention 14 daily / 8 weekly / 12 monthly; verification after each backup; step-by-step restore guide and script; restore tested before backups are reported as working.
- Laptop: the NAS share is mapped as a drive/folder and given in the configuration file; a Windows scheduled task (or the Docker backup service) runs nightly while the laptop is on.
